# 9処理系 実行速度ベンチマーク — 競プロと科学計算のあいだ

C / Rust / Julia / Go / Java / Node / Bun / PyPy / LuaJIT で、同じアルゴリズムを素直に書いたときの計算速度を比べた記録。

- 実施日: 2026-11-03
- 目的: 「計算力」と「科学計算にどの程度向いているか」を測る

---

## 1. 結論(先に要点だけ)

1. **総合1位は C、僅差で Rust、3位は Julia。** 4種目の合計は C 53.9 秒、Rust 56.6 秒、Julia 70.2 秒で、4位の Go(119.2 秒)以下を大きく離した。
2. **差を生んだのは言語そのものより、コンパイラの最適化とメモリの使い方。** ベクトル化が効く整数ループでは、C/Rust が他の 10〜20 倍速かった。メモリの速さで決まる篩では、上位がほぼ横並びになった。
3. **同じ三重ループでも、メモリの並び方だけで 2 倍の差が出た。** 行列積で Julia が 1 位になった理由は「列優先」という配列の並び方だった。C で同じ並びにすると、C も同じ速さになった。
4. **科学計算は素直なループよりライブラリが圧倒的に速い。** NumPy / Julia の `A*B`(中身は BLAS)は 0.17 秒で、素直な C の約 100 倍速かった。
5. **書き方ひとつで大きく変わる。** Rust は `for z in 0..=n` を `0..n + 1` に変えただけで、方程式が 51.0 秒から 6.6 秒になった。

### ルール

- 全処理系で**同じアルゴリズム**を、その言語で**素直に**書く。手作業の最適化はしない(例外は 6.3 の Rust)。
- 時間は各プログラムの中で**計算部分だけ**を測る。起動時間は含まない。JIT のウォームアップは含む。
- 結果の値を出力し、**全処理系で答えが一致する**ことを確認する。これで実装の誤りや、コンパイラが計算を丸ごと省略することを防ぐ。
- 問題サイズは **Go で約 30 秒**になるように合わせ、全処理系で同じサイズを使う。
- 1 種目ずつ順番に実行する(同時には走らせない)。各 1 回だけ計測。

## 3. 種目

| 種目 | 内容 | サイズ | 主に測っているもの |
|---|---|---|---|
| 篩 | N=10⁷ のエラトステネスの篩を繰り返す | 600 回 | 配列への書き込み(メモリの速さ) |
| bit全探索 | n 個の重みから、和が総和/2 になる組合せを 2ⁿ 通り数える | n=28 | ビット演算と、予測しにくい分岐 |
| 方程式 | 0≤x,y,z≤N で x²+y²+z²=N² の解を三重ループで数える | N=3000 | 整数ループの最適化(ループの外に出す・ベクトル化) |
| 行列積 | n×n の小数(float64)行列の積を i-j-k の三重ループで計算 | n=1750 | 小数の計算、キャッシュの使い方 |

行列積の入力は、a[i][j] = ((i·j) mod 7 + 1)/8 と b[i][j] = ((i+j) mod 5 + 1)/4。値がすべて 2 の累乗分の 1 の倍数なので、和に丸め誤差が出ない。そのため、計算順序の違いや FMA 命令の有無に関係なく、全処理系で答えがぴったり一致する。

## 5. 種目ごとの分析

### 5.1 篩 — メモリの速さが上限になる

C・Rust・Julia・Go が 30 秒前後で横並びになった。篩の中身はほとんど「配列のあちこちに 1 を書き込む」処理なので、計算よりメモリへの書き込みの速さで時間が決まる。コンパイラがいくら賢くても、縮められる余地がほとんどない。

- **LuaJIT が 177 秒で最下位。** Lua の表(table)は 1 要素あたり何バイトも使うので、1000 万要素の表を毎回作り直すのが重い。言語の遅さというより、データ構造の選び方の差が大きい。LuaJIT の FFI で C の配列を使えば、大きく縮むはず。
- **Node(40.2 秒)が Bun(48.5 秒)より速い。** 同じ JS コードでも、エンジンによって得意な処理が違う。

### 5.2 bit全探索 — 分岐をなくせるかで 20 倍差

C 1.4 秒、Rust 2.0 秒に対し、ほかは 20 秒以上かかった。

- `if ((mask >> i) & 1)` の当たり外れはほぼランダムなので、CPU の分岐予測が外れやすい。
- gcc や LLVM は、この分岐を**分岐のない形**(条件付きの加算)に変え、さらにベクトル化までできると考えられる。そうすると予測ミスの損がなくなる。
- Java(21.6 秒)が Go(29.3 秒)に勝ったのは、Java の JIT(C2)がループ展開や分岐の除去を Go のコンパイラより積極的にやるためと推測している。アセンブリは未確認。

### 5.3 方程式 — 「ループの外に出す」最適化の有無

内側の z ループでは、`x*x + y*y` は変わらないので、本来はループの外で 1 回計算すれば済む。

- **JIT 勢(Node・Bun・LuaJIT・PyPy)が Go と互角以上だった。** V8 などの JIT は、ループの中で変わらない計算を自動で外に出していると考えられる。Go のコンパイラはコンパイルの速さを重視していて、ここまではやらない。実際、Go で手で外に出すと 29.7 秒が 16.7 秒になった。
- **LuaJIT は 20.3 秒で、C・Rust・Julia を除けば最速だった。**
- **C・Rust・Julia は 5〜7 秒。** ループの外に出したうえで、さらにベクトル化までしていると考えられる。

### 5.4 行列積 — メモリの並び方で 2 倍差、ライブラリとは 100 倍差

**Julia が 8.7 秒で 1 位。** 原因は配列の並び方だった。

- C・Rust・Go などは**行優先**(横方向にメモリが並ぶ)。i-j-k の順のループでは、一番内側で行列 B を縦に飛び飛びに読む。i が 1 つ進むたびに B 全体(約 24MB)をメモリから読み直すことになる。
- Julia は**列優先**(縦方向にメモリが並ぶ)。同じ i-j-k の順で書くと、飛び飛びに読むのは A の 1 行(約 14KB)だけになる。この行は j が進む間ずっと同じなので、キャッシュに残ったまま使い回せる。
- 確認として、C で配列を列優先の並びに変えると、17.6 秒が 8.2 秒になり、Julia と同じ速さになった。つまり Julia の勝因は言語の速さではなく、データの並び方だった。

そのほかの観察:

- **小数になって C の圧勝が消えた。** 整数の種目では C は他の 10 倍以上速いこともあったが、行列積では Go との差が 2 倍以下だった。小数の足し算は順番を入れ替えると結果が変わるので、コンパイラは足し算をまとめてベクトル化することができないためと考えられる。
- **Java が 50.7 秒と遅め。** Java の `double[][]` は、行ごとに別々の場所に置かれた配列の集まり。B を縦に読むときに、行をたどる手間が毎回かかっていると考えられる。
- **ライブラリ(BLAS)は 0.17 秒で、素直な C の約 100 倍速い。** データをキャッシュに収まる小さなブロックに分けて計算し、ベクトル命令をフルに使っているため。科学計算や AI(PyTorch など)で自前のループを書かずにライブラリを使う理由が、この数字に表れている。

## 6. 横断的な考察

### 6.1 JIT 言語は「素直なコード」で健闘する

方程式では、Node・Bun・LuaJIT・PyPy が、事前にコンパイルする Go と互角かそれ以上だった。JIT は実行中のふるまいを見て最適化するので、整数の単純なループには強い。一方で、篩のようにデータ構造の作りが効く処理や、Bun の行列積のように、エンジンの得意不得意で大きく崩れることもある。

### 6.2 PyPy と CPython

同じ `bench.py` で、PyPy は CPython より 10〜70 倍速かった。ただし PyPy も、配列アクセスの多い篩(78.5 秒)と行列積(69.2 秒)では、上位との差が大きい。

### 6.3 Rust の `..=` 問題

`for z in 0..=n`(終わりの数を含む範囲)は、Rust では最適化が効きにくくなる書き方として知られている。`0..n + 1` に書き換えただけで、方程式が 51.0 秒から 6.6 秒になった。表の Rust の数字は書き換え後のもの。**Rust にだけ手を入れた**ことになるので、厳密にはルールの例外。同じ範囲の書き方でも、Julia の `0:n` は問題なく最適化された。

### 6.4 C と C++

gcc と g++ は中の最適化エンジンが共通なので、同じ書き方ならほぼ同じ速さになる。篩 60 回で比べると、C 2.97 秒、C++ `vector<char>` 3.00 秒、`vector<bool>` 3.13 秒だった。

### 6.5 科学計算への向き・不向き

| 観点 | 結果から言えること |
|---|---|
| 素直なループの計算力 | C・Rust が最上位。Julia も、JIT 言語なのに C に迫る |
| 小数の計算 | C/Rust の優位は縮み、メモリの並び方の影響が大きくなる |
| 実際の科学計算 | ライブラリ(BLAS など)を使うのが前提。素直なループとは 100 倍の差がある |
| 総合 | 「素直に書いても速く、ライブラリも標準で使える」Julia は、科学計算向けという看板どおり |

## 7. このベンチマークの限界

- **各 1 回だけの計測。** クラウド環境なので数 % の誤差がある。接戦の順位は、3〜5 回測って中央値を取らないと確定できない。
- **最適化オプションが対等ではない。** C・Rust だけ `-march=native` を付けている。Go・Java・JS には相当するオプションがほとんどない。
- **データ構造が対等ではない。** 篩の配列は、Python は `bytearray`、Lua は普通の表。Java は `double[][]`、C は 1 次元の配列。どれもその言語で素直な書き方を選んだが、速さへの影響は大きい。
- **計算以外のスレッド。** Java・JS は JIT コンパイルや GC を別スレッドで実行でき、2 コア目を使える。
- **測れていないもの。** ハッシュマップ、たくさんのオブジェクトを作る処理(GC の性能)、再帰、文字列処理。実際のアプリで差が出やすいのはこれらの処理。
- **ルールの例外。** Rust だけ範囲の書き方を修正した(6.3)。

### 次にやるなら

- 3〜5 回計測して中央値を取る
- 小数の種目を追加する(N 体シミュレーション、2 次元の熱拡散)
- 「ライブラリあり部門」を正式な種目にする(NumPy、Julia 標準、Java の行列ライブラリなど)
- 工夫してよい範囲(ループの外に出す、範囲の書き方など)を最初に決めておく
